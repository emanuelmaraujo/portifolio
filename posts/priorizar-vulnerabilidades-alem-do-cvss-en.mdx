A scan report usually arrives with hundreds of findings, and the first instinct is to sort it by score: criticals first, then highs, and so on. The rule is easy to explain and easy to audit. The trouble is that it answers a different question from the one the team needs answered.

The score says how bad a flaw can be. The team needs to know which flaw, in this environment and this week, is most likely to become an incident.

## What CVSS measures

CVSS (the Common Vulnerability Scoring System) is maintained by FIRST and describes the technical characteristics of a vulnerability: how it is reached, which privileges it needs, whether it depends on user interaction and what it does to confidentiality, integrity and availability. The result is a score from 0 to 10, which version 3.1 translates into ratings:

| Rating | Base score |
|---|---|
| None | 0.0 |
| Low | 0.1 to 3.9 |
| Medium | 4.0 to 6.9 |
| High | 7.0 to 8.9 |
| Critical | 9.0 to 10.0 |

The CVSS user guide itself has a section titled “CVSS Measures Severity, not Risk”, and NIST's vulnerability database repeats the warning. The base score is calculated once, for every environment in the world. It does not know whether anyone is exploiting the flaw, whether your server is exposed or what that server supports.

<Callout title="Severity and risk">
Severity is a property of the flaw. Risk is what happens when the flaw meets a threat and an asset that has value. One vulnerability has a single severity and as many risks as there are places where it appears.
</Callout>

The standard allows for that adjustment. Version 4.0, published in November 2023, arranges its metrics in four groups (Base, Threat, Environmental and Supplemental) and adopts a naming scheme that states what was considered: CVSS-B is the base alone, CVSS-BT adds threat, CVSS-BE adds the environment and CVSS-BTE has all three. In practice almost every score that circulates in reports is the base. Sorting the queue by it alone is using half of the standard.

## Threat: is anyone exploiting it?

The first missing context is the threat. According to FIRST, only around 5% of published vulnerabilities are ever exploited. Knowing which ones changes the queue more than any decimal place of the score.

Two public sources help:

- **KEV (Known Exploited Vulnerabilities)**, from CISA, is a catalogue of vulnerabilities with confirmed exploitation. It began with directive BOD 22-01 of November 2021, which gave US federal civilian agencies deadlines to remediate whatever entered the list. In June 2026 that directive was superseded by BOD 26-04, which sets update deadlines by risk. Even for those not bound by it, the catalogue answers a plain question: has this been used in attacks?
- **EPSS (Exploit Prediction Scoring System)**, from FIRST, estimates the probability, from 0 to 1, that a vulnerability will be exploited in the next 30 days. Scores are updated daily and come with a percentile, which places the flaw relative to all the others.

The two complement each other. KEV records what has happened, and EPSS estimates what is likely to. Neither knows your environment.

Querying both is simple enough to belong in any triage routine:

```python
import json
from urllib.request import urlopen

EPSS = "https://api.first.org/data/v1/epss?cve={}"
KEV = "https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json"


def load_kev() -> set[str]:
    with urlopen(KEV) as response:
        catalogue = json.load(response)
    return {item["cveID"] for item in catalogue["vulnerabilities"]}


def query_epss(cve: str) -> tuple[float, float]:
    with urlopen(EPSS.format(cve)) as response:
        data = json.load(response)["data"]
    if not data:
        return 0.0, 0.0
    return float(data[0]["epss"]), float(data[0]["percentile"])


kev = load_kev()
for cve in ["CVE-2021-44228"]:
    probability, percentile = query_epss(cve)
    print(cve, "KEV" if cve in kev else "-", f"EPSS {probability:.3f}", f"percentile {percentile:.2f}")
```

## Exposure: can the flaw be reached?

The second context is the path to the asset. A remote code execution flaw in a service published on the internet and the same flaw on a lab server with no inbound route share a score and carry very different risks.

For each relevant finding it is worth answering:

- Is the vulnerable service exposed to the internet, to partners or only to the internal network?
- Is there segmentation between it and ordinary users?
- Is the vulnerable component actually in use, or merely installed?
- Is there a compensating control that has been tested, such as a WAF rule or the affected feature being disabled?

These answers depend on a reliable inventory. Without knowing what exists and where, prioritising by context becomes opinion.

## Asset criticality and business impact

The third context is the value of what is at stake. Here the question stops being technical: if this asset stops, leaks or is altered, what happens to operations, to customers and to regulatory obligations?

Many organisations express this as a likelihood by impact matrix. The matrix is useful for talking to decision makers, as long as it is clear what it is: a policy written in the shape of a table.

## Turning the signals into a decision

With severity, threat, exposure and criticality on the table, it is tempting to multiply everything and produce a new score. The result looks precise and hides the reasoning.

An alternative is the one taken by SSVC (Stakeholder-Specific Vulnerability Categorization), created by CERT/CC and used by CISA. Instead of a score, it walks a decision tree with questions such as the state of exploitation, whether the attack can be automated, the technical impact and the effect on mission and public well-being. The output is an action: Track, Track*, Attend or Act.

A few practices make the process defensible in an audit:

1. **Write the rule down.** The policy should say which signals are considered and which deadline each class receives. Control 8.8 in Annex A of ISO/IEC 27001:2022 asks for the management of technical vulnerabilities, and CIS Control 7 covers managing them continuously. Neither requires sorting the queue by CVSS.
2. **Record the decision, not only the fix.** Staying at “track” is a valid decision when it has a justification, an owner and a review date.
3. **Reassess when the context changes.** A new KEV entry, or a service that became exposed, changes the class without the score changing.
4. **Measure by class.** The average time to remediate everything hides what matters. Follow how long flaws in the most urgent class stay open and how many exceptions have expired.

## Limits of the approach

Prioritising by context asks for more than prioritising by score, and it is honest to state the costs:

- **It depends on data.** An outdated inventory and generic criticality ratings produce wrong priorities that look methodical.
- **EPSS is a probability.** A low score does not guarantee the flaw will not be exploited, and the model is global, not specific to your sector.
- **KEV is late confirmation.** A flaw enters the catalogue after exploitation has been observed. Absence from the list does not mean safety.
- **Compensating controls age.** A blocking rule nobody tests again stops being a control.
- **It does not replace hygiene.** NIST's patch management guide (SP 800-40 Rev. 4) treats patching as preventive maintenance. Prioritisation decides the order. It is not permission to leave the rest unpatched indefinitely.

The CVSS score remains useful as a starting point and as a common language with vendors. Deciding what to fix first also needs the threat, the exposure and the value of the asset, and it needs to be written in a way someone else can repeat.
